## What This Thread Was Doing

g01.007 landed the `rich_text` block. This lane takes the next core-vocabulary
piece: retiring the extracted `media` type and replacing it with `download_card`,
which is the one generic block that keeps a media-library reference.

The operator's direction replaced an earlier plan. The previous design gave one
`registerMediaSource({ pick, resolve })` seam three consumers — the image block,
the media block, and the rich-text image node. That plan is gone: images are
URL-based like Poodle's rich-text image node, embeds are Poodle's `ParsedEmbed`,
and only the download card needs the library.

## Why It Matters

`media` is three things wearing one name. Its editor normalises block data to
`{ media_id, caption, alt, display }`, where `display` offers inline, block,
float-left and thumbnail — image presentation — and there is no download
presentation at all. It also has no renderer, so the type is declared, editable
and unrenderable.

Splitting it fixes the vocabulary and closes a real gap: downloads are the one
media case where a generic block must hold a reference the consumer owns, because
a file's name, size and URL belong to the library, not to the content.

## Boundaries

- **In scope:** the new Svelte-free media-source registry and its subpath; the
  `download_card` editor, renderer and empty checker; the `media` retirement with
  every surface it reaches; the tests that assert or name either.
- **Out of scope:** the `image` and `video` blocks, the `table` and `item_list`
  editors, the rich-text host function, the Rust crate, the wire fixtures,
  release or version changes, and every consumer repository.
- **Repo constraints:** follow `AGENTS.md` and contracts 002 and 003. The
  registry module must import neither Svelte nor any editor module, because both
  the editor and the renderer import it. The renderer carries no scoped styles, no
  new CSS class and no new token; it emits
  `data-nightfire-block="download_card"`. Editors may style themselves, as the
  existing editors do. Do not add a dependency.
- **Clean break:** no `media` alias, no compatibility shim, and no migration.

## Important Context

- **Planning lineage:** the vocabulary was declared and then revised on
  2026-09-18. The revision is the operator's: `download_card` keeps the library
  hook, and images and embeds do not use it. The architecture document is the
  authority; the earlier handover's media bullets are marked superseded.
- **How the plan fits the system:** `ts/src/core-blocks.ts` is the declaration and
  `ts/tests/nightfire/core-self-registration.test.ts` asserts it in both
  directions — every declared capability is registered, and nothing undeclared is
  registered. Flip a flag only in the change that registers the part.
- **Two constraints that are easy to miss.** The registry must be module-level
  rather than a Svelte context, because a renderer must resolve references too and
  cannot reach a context provider. And `resolve` must be synchronous, so the
  renderer and SSR stay simple: the consumer resolves over metadata it has already
  loaded, and an unknown reference renders inert rather than suspending.
- **Retirement is consumer-visible.** `./media` is a published subpath in `0.1.0`,
  and it is also where `MediaKind` and the `media-locator` re-exports currently
  reach some consumers. `./media-locator` keeps its own subpath, so a consumer
  that imported locator helpers from `./media` must move to `./media-locator`.
  State that in the PR description; the Acowtancy adoption lane carries the
  consumer side, not this repository.
- **Open tensions:** none for this lane. The `image.sizing` preset names are the
  one open vocabulary item, they belong to g01.012, and they must not be decided
  here.

### UI design brief (compact)

- **Classification / current and target workflow:** refinement. The author picks
  one or more files from the consumer's library, then optionally describes the
  card and each file. No new visual language and no new interaction pattern.
- **Presentation direction and design authority:** semantic markup, the
  `data-nightfire-block="download_card"` hook, data attributes for structure, and
  the consumer's own appearance. Contract 003 rules 1–4.
- **States, content ranges, and input envelope:** no source registered → rows
  render inert; registered but an unresolved reference → that row renders inert
  and is marked; resolved → filename, size, type, description and a download
  link; empty file list → nothing renders. A card with one file and a card with
  many must both work.
- **Selected concept or prototype identity:** none required at this
  classification.
- **Scenario oracle:** register a source, pick two files, describe the card and
  one file, save, reload, and confirm both rows render from the same references
  and the descriptions survive. Then unregister the source and confirm the same
  block renders inert rather than throwing.
- **Open decisions and stop conditions:** none. Stop rather than inventing a
  presentation or a library capability.
